## Evaluation of the Flux-Conservation Deviation

### 1. Shader Math vs. Quad Footprint
- **Analysis:** In `kSplatShader`'s `vs_main`, vertices are offset in the tangent frame by a displacement proportional to `radius`. This results in the rasterized on-screen footprint of each surfel having an area $A_{screen} \propto \frac{radius^2}{distance^2}$.
- **Fragment Shader:** In `fs_main`, the radiance of each covered fragment is computed as `radiance = color * brightness * camera.exposure * alpha`. For a given distance, the total screen light (luminous flux) emitted by a surfel is the integral of the fragment radiance over its projected area, which yields $Flux \propto brightness \cdot radius^2$.
- **Conclusion:** Yes, the shader math implies that a surfel's total emitted light is proportional to $brightness \cdot radius^2$. Summing the brightness directly during merges while growing the radius (as suggested by the architecture doc's `brightness = Σ children.brightness`) would result in a massive artificial amplification of energy. Conservatively scaling brightness by $\frac{fluxSum}{radius^2}$ is mathematically necessary under this rendering model to avoid the image blowing out to solid white.

### 2. Implementation of the Merge Formula
- **Analysis:** In `BuildHierarchy`, the parent's attributes are calculated as follows:
  - `fluxSum` accumulates the flux of each child node: `fluxSum = Σ (child.brightness * child.radius^2)`.
  - The parent `radius` is calculated as the minimum covering radius enclosing all children: `radius = max(distance(parent, child) + child.radius)`.
  - The parent `brightness` is computed as `fluxSum / (radius * radius)` if `radius > 0.0f` (and `fluxSum` otherwise).
- **Conclusion:** This matches the correct flux-conservation formula $\text{brightness}_{parent} = \frac{\sum_i \text{brightness}_i \cdot \text{radius}_i^2}{R^2}$ exactly.

### 3. Verification of Flux Conservation Telemetry
- **Analysis:** On startup and regeneration, `DumpHierarchyStats` computes the root node flux, the sum of all leaf node fluxes, and the relative error between them:
  - `leafFlux` is computed directly by summing $brightness \cdot radius^2$ over all leaves.
  - `nodeFlux(root)` is evaluated directly on the root node.
  - At runtime, running the application prints:
    ```
    [hierarchy] leaves=60000 nodes=80002 levels: 60000 15000 3750 938 235 59 15 4 1
    [hierarchy] flux root=333.137 sum(leaves)=333.137 sum(root.children)=333.137 rel.err(root vs leaves)=1.50037e-07
    ```
- **Conclusion:** This confirms that the total luminous flux is conserved across all levels of the merge hierarchy down to float precision limits.

### 4. Integrity of Leaf-Level Values
- **Analysis:** In `BuildHierarchy`, level 0 leaf nodes are populated directly from `stars[i]` using the unmodified values generated by `GenerateStar` (which maintains the exact same RNG draws and parameters as Part 1).
- **Conclusion:** Leaf-level nodes are untouched by the flux-conservation math. The original full-detail appearance of the galaxy is preserved when zoomed in.

### 5. Architectural Assessment
- **Assessment:** Flux conservation is the correct and necessary physical interpretation of Design Principle 2 ("energy-conserving merges"). We recommend amending the formula in `docs/galaxy_architecture.md` to reflect the surface-radiance scaling factor ($\frac{\sum_i b_i r_i^2}{R^2}$) rather than the point-luminosity summation.

## Findings & Evidence for Checklist Items

### 6. Morton Code / Tree Construction Correctness
- **Finding:** The Morton-code quantization and Z-order bit interleaving are mathematically correct and free of sign, axis, or overflow bugs.
- **Evidence:**
  - Coordinates are shifted to positive space by subtracting the AABB minimum `boundsMin.x/y/z` and scaled to `[0, 2097151]` (fits in 21 bits), preventing sign errors or overflows.
  - `SpreadBits21` utilizes a correct bit-spreading sequence that places the 21 bits of coordinate values into every third bit position (`0, 3, 6, ..., 60`).
  - `Morton3D` correctly shifts the spread coordinates by 0, 1, and 2 bits to interleave them into a 63-bit code.

### 7. `starCount` Dual-Role Split
- **Finding:** The separation between `starCount` (true Milky-Way scale) and `generatedStarCount` (render budget) was implemented cleanly.
- **Evidence:**
  - Ripgrep search confirms that `.starCount` is only referenced in telemetry printouts.
  - Loop bounds, leaf counts, preset load/save paths, and ImGui sliders are all driven exclusively by `generatedStarCount`.

### 8. Buffer Safety
- **Finding:** Traversal limits and rendering buffers are safe from overflows and display artifacts.
- **Evidence:**
  - `SelectCut` is guarded by `if (cutSurfelCount_ >= kMaxCutSurfels)` which guarantees that the traversal stops emitting before exceeding `kMaxCutSurfels` (16384).
  - The GPU draw call (`pass.Draw(cutSurfelCount_)`) and vertex upload (`queue.WriteBuffer`) only process the active prefix, meaning any leftover data in the unwritten tail of the buffer is ignored.

### 9. Hysteresis Correctness
- **Finding:** The LOD tree-cut traversal correctly implements the asymmetric hysteresis logic.
- **Evidence:**
  - In `SelectCut`, if the node was expanded last frame (`wasExpanded` is true), the threshold is scaled down by `(1.0f - kLodHysteresisBand)` (0.75x), keeping it expanded. If merged last frame, the threshold is scaled up by `(1.0f + kLodHysteresisBand)` (1.25x), keeping it merged.

### 10. `pixelErrorThreshold` Control Scope
- **Finding:** Adjusting the "Pixel Error" slider does not trigger a full galaxy regeneration.
- **Evidence:**
  - The return value of the ImGui slider is ignored and does not set `galaxyDirty_`. It only modifies the traversal threshold used during `BuildAndUploadCut()` which runs dynamically every frame.

### 11. Compilation Verification
- **Finding:** The project compiles cleanly with zero warnings under `-Wall -Wextra -Wpedantic`.
- **Evidence:**

### 12. File Scope Compliance

## Open Questions

1. **Star Scale Calibration:**
   The true `starCount` remains purely cosmetic. A future task should calibrate the GenerateStar's density normalization using this parameter.
2. **Frustum Culling for Close-Ups:**
   When zoomed in very close, the LOD traversal hits the fixed capacity cap `kMaxCutSurfels` (16384) and halts further expansion. Implementing frustum culling would allow the render budget to be spent only on visible nodes, resolving the cap bottleneck.
